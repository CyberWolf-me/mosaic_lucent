# Lucent — Agent Team and Operating Contracts

> Roles, worker contract shape, and retry/escalation rules for the CTO-agent
> control plane. Normative state machine: `scripts/cto/lib/spec.js`
> (`TRANSITIONS`). Task specs: `tasks.json`. Runtime state: `.cto/`.

## 1. Roles (spec §5)

Five responsibilities; they are not five always-on processes. For a
solo-founder setup, one agent may cover Implementation end to end, and the
CTO may double as reviewer only for low-risk tasks — never for high-risk
ones (no self-approval extends to role-doubling: the reviewer must be a
different execution context than the implementer).

- **CTO orchestrator** — priorities, decomposition, contracts, conflict
  resolution, review assignment, integration decisions, final sign-off.
  Cannot override security/approval policies to finish faster.
- **Product / research** — clarifies intended behavior, maps requirements
  to acceptance criteria, identifies existing capabilities. Read-only:
  research tasks carry file-less or docs-only scopes.
- **Implementation** — owns the assigned change in its worktree, respects
  the contract, runs declared checks, records limitations, submits for
  review. Never marks its own work verified or done.
- **QA / testing** — owns evidence evaluation: checks that the passing
  suite actually covers the acceptance criteria, runs typecheck/regression
  gates, names the gap between green tests and real acceptance.
- **Security / DevOps** — reviews authorization, secrets, migrations,
  deployment and operational risk. Owns `SECURITY.md` edits only when the
  assigned task requires them.

Split agents when they need different expertise, tools, permissions, or
evaluation criteria — not before (coordination overhead is real).

## 2. Worker contract

Every dispatch delivers the complete contract, not a title. Generated by
`node scripts/cto/context.mjs <task> --worker <id>`:

- Task ID + spec revision (`spec_rev` — the worker pins what it built
  against; a spec change mid-flight is visible, never silent).
- Role + worker identity, branch + worktree assignment.
- Objective, acceptance criteria, dependencies and their states.
- Allowed paths / prohibited paths (enforced by `integrate.mjs`, not by
  prose).
- Verification commands with cwd, required gates, evidence requirements.
- Retry policy (default: ≤2 automatic attempts, then CTO reassesses) and
  escalation conditions (blocker, scope change, secret encountered,
  destructive operation).
- Approval requirements (founder gates are named, never implied).

## 3. Worker return obligations

A submission must include: result summary; files/interfaces changed; tests
and checks actually executed with real output (exit codes, counts);
assumptions and open questions; known limitations, failures, blockers.
Claims are validation input, not proof — `verify.mjs` re-runs the checks
against the recorded revision.

## 4. Retry and escalation

- Bounded retries: at most `retry_policy.max_automatic_attempts` (default
  2); each retry records the previous failure and changes the approach —
  blind repetition is a policy violation.
- Escalate to the founder: product scope trade-offs, irreversible or
  destructive actions, unexpected costs, security-sensitive actions,
  anything beyond CTO authority. Escalation is recorded as an event with
  the decision requested, never as chat alone.
