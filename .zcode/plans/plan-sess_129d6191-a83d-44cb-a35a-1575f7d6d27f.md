# Finishing the remaining plan verticals

Two Explore agents audited the actual code. Key discovered facts that shape this plan:

- **MCP** (`packages/mcp`): `BoardSession` holds a `Workspace` in memory and is *injected* into `createDispatcher(session)` + `serveStdio()` — one seam to swap. No HTTP-client dep exists; Node 22's global `fetch` is what the e2e harness already uses. CSRF deliberately bypasses bearer-only clients (the app.ts:995 comment anticipates "the MCP client's bearer path").
- **No op-apply HTTP route exists** — ops reach a board via WebSocket (`{type:"op"}` → `Room.commit` with server-assigned seq, re-validation each round) or `/api/generate`'s authoritative path. So MCP-to-real-boards needs **one new server route**, not just MCP changes.
- **LiveKit**: the web client already implements `POST config.tokenUrl` expecting `{token, url?}` and the Settings placeholder is literally `/api/livekit/token` — a route that does not exist server-side. Building it *completes an existing client contract*. The `voice.minutes` entitlement + `voice.minute` usage kind exist but nothing meters them.
- **MeetingView** is a labeled design preview (hardcoded transcript, "NOT RECORDING" badge); no transcript persistence exists anywhere.
- **Audit**: `auditFor(orgId, limit, cursor?)` has keyset pagination in the store but the route hardcodes 100 and accepts no cursor; no export of any kind.
- **Bearer auth** works today via the 7-day HMAC session token from signup/login (`token` in the response body) — `verifyToken(bearer, ctx.secret)` in `authenticate`. No PAT concept exists.
- **SAML**: zero XML libraries in the lockfile; SAML proper therefore adds a dependency — decision recorded in an ADR.
- Migrations sit at **0014** (empty journal marker); next is **0015**.

Your two decisions are folded in: **SAML 2.0 proper** for SSO, and **server vertical + live capture** for meeting mode.

## R1 — MCP to real boards (the product-critical gap)

**Server: one new route.** `POST /api/boards/:id/ops` in a new `packages/server/src/routes/boardOps.ts`, registered on the Router:
- Bearer or cookie auth → `requireBoardRole(..., "editor", ...)`.
- Body `{ ops: Operation[], label?: string }`. Pipeline mirrors `Room.commit` exactly: filter human-only ops → `stampAuthorship(ops, userId)` (the **caller's real user id**, not ASSISTANT_AUTHOR) → `repairOperations` → `validateOperations` against the stored board's workspace → on failure `422 { error, errors }`.
- On success: `boardStore.appendOp(...)` then `boardStore.put({workspace, updatedAt})`, mirroring generate.ts's authoritative path (single-writer HTTP; no room seq dance — the op log records `label` + `by`).
- Metered via the same `lucent_http_requests_total` route label; audit-logged as `board.agent_ops` with a metadata count.

**MCP: swap the session, keep the surface.**
- New `packages/mcp/src/remote.ts` exporting `RemoteBoardSession implements` the same `callTool` contract as `BoardSession`:
  - Constructor takes `{ baseUrl, token, boardId, fetchImpl? }` from new env vars `LUCENT_MCP_URL`, `LUCENT_MCP_TOKEN`, `LUCENT_MCP_BOARD` (documented in `.env.example`; absent → today's in-memory `BoardSession` remains the default, so the package never hard-requires a server).
  - `get_board` → `GET /api/boards/:id` (uses the server's role check + full workspace), then reuses the existing `summarizeBoard` (export it from tools.ts).
  - `apply_canvas_operations` → validate **pre-roundtrip** exactly as the plan requires: `validateOperations(localWorkspace, stampedOps)` locally first (catches malformed batches for a precise error before any network call), then `POST /api/boards/:id/ops`; server 422 errors map to the same "Rejected N invalid operation(s)" text the current session emits.
  - `reset_board` → refuses with a clear message on the remote session (no server-side destructive reset exists; that's honest, not a gap).
- `main.ts` picks `RemoteBoardSession` when `LUCENT_MCP_URL` is set, else `BoardSession`. `createDispatcher` and the 3-tool surface are untouched — **zero MCP-protocol change**.
- Tests: new `packages/mcp/test/remote.test.ts` boots the real server via the collab.e2e harness pattern (signup → seed board → drive `RemoteBoardSession`): roundtrip sync (MCP `get_board` matches server), invalid batch rejected pre-roundtrip, valid batch lands on the server and survives a second MCP `get_board`, viewer token → 422, wrong-board 404. Existing `mcp.test.ts` stays green for the local session.

**Gate**: mcp + server suites green; a documented `LUCENT_MCP_*` block in `.env.example`.

## R2 — LiveKit server-minted tokens (completes the web's existing contract)

- `packages/server/src/livekit.ts`: `mintLiveKitAccessToken({ apiSecret, apiKey, room, identity, name?, ttlSeconds })`. LiveKit tokens are **JWT HS256 with a defined grant payload** (`video: { room, canPublish, canSubscribe }`, `metadata`); implement JWT signing with `node:crypto` HMAC + base64url — no new dependency, verified against LiveKit's documented token format, with a test asserting the decoded grant shape (correctness is in the header/payload/signature structure, which we can pin without a LiveKit account).
- Config: `LUCENT_LIVEKIT_URL` (wss://…), `LUCENT_LIVEKIT_API_KEY`, `LUCENT_LIVEKIT_API_SECRET` in `config.ts` + `.env.example`; unset → route answers 503 (the same fail-open pattern as billing).
- Route `POST /api/livekit/token` in app.ts: `requireUser` (cookie or bearer) → mint `{ token, url: LUCENT_LIVEKIT_URL, ttlMs }` → **meter `voice.minute` is NOT metered here** (hosted-voice metering happens on STT usage in the web flow, and only when LiveKit is the STT provider — deferred with a comment; entitlement plumbing exists, metering without real usage would be a lie).
- Tests: token structure (HS256 header, `video.room` grant = requested room, `identity` = user id, exp = now+ttl), tamper rejection, 503 when unconfigured, 401 anonymous. Web needs no change — the settings placeholder already points at this route.

## R4 — SAML 2.0 per-org SSO (your chosen scope)

- **ADR 0013: SAML dependency choice** — decision: add `@xmldom/xmldom` (parse) + hand-rolled **exclusive canonicalization (exc-c14n)** + `node:crypto` `verify("rsa-sha256")` for signature checking, rather than a SAML framework (samlify/passport-saml). Rationale: the server has no framework anywhere (ADR 0002), passport-saml drags express-era assumptions, and the SAML surface we need is exactly: parse Response → canonicalize signed elements → verify RSA signature against the IdP cert → extract NameID + attributes. Recorded with the escape hatch (swap to a library if IdP interop wobbles).
- **Migration 0016_sso.sql**: `sso_connections (id pk, org_id FK CASCADE, idp_entity_id, acs_url, x509_cert_pem, name_id_format, enforce_sso bool default false, created_at)` + unique `(org_id, idp_entity_id)`; `domain_claims (id pk, org_id FK CASCADE, domain unique, verified_at, token)` for domain claiming; JIT provisioning rides the existing users/memberships tables (no new table).
- `packages/server/src/saml.ts`: `parseSamlResponse(xml)` (rejects enveloped-signature-wrapped attacks by verifying the **Response** signature, not the Assertion's, when both present), `verifySamlSignature(node, cert)`, `canonicalize(node)` (exc-c14n), `nameIdAndAttributes(parsed)`; `InMemorySsoStore` + `store/pg-sso.ts`.
- Routes (`packages/server/src/routes/sso.ts`): owner-only `PUT /api/orgs/:id/sso` (upload IdP metadata fields + cert), `POST /api/orgs/:id/sso/claim-domain` (TXT-token challenge issuance), and the ACS endpoint `POST /api/auth/saml/:orgId/acs` (open by design — validates signature against the org's stored cert, then JIT-provisions: find-or-create user by email, grant org membership, mint session; when `enforce_sso` is set, the password-login route refuses claimed-domain emails with a "sign in with SSO" message instead of a credential check).
- Web: AdminView SSO section (paste metadata, upload cert, claim-domain flow showing the TXT record, enforce toggle), sign-in card renders "Continue with SSO" when a claimed-domain email is typed.
- Tests: full flow against a **mock IdP** in tests (self-signed RSA keypair minted in-test, real XML, real signatures) — valid response authenticates + JIT-provisions; tampered assertion rejected; wrong-org cert rejected; `enforceSSO` blocks password login for claimed domain; replayed Response (InResponseTo/NotOnOrAfter window) rejected. Parity tests for the store.
