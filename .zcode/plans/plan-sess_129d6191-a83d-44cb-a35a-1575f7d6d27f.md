# Stage B — Platform Core: complete the multi-user operation protocol

## The honest baseline (from the code audit)

The advisory's B1–B8 (identity, auth, sessions, /me, orgs, memberships, invitations, board permissions) **already ship and are hardened** — `usr_` IDs, password+TOTP+OAuth(Google/GitHub)+SAML+SCIM, revocable sliding sessions, org→board tenancy with server-side `roleAtLeast` guards on every route including realtime, SHA-256-hashed invites, audit log. B13–B17 and B24 (revisions, rooms, presence, cursors, whole-batch concurrency) also ship with **stronger semantics than the advisory proposes** (validated batches with precondition rejection, not last-write-wins).

So Stage B is **not** a build of the platform core — it is the completion of the four things that genuinely don't exist, which are exactly the ones that make shared boards untrustworthy:

| Real gap | Advisory # | Today |
|---|---|---|
| Server-side proposals | B9/B10/B27 | localStorage only (the P2 boundary) |
| Request idempotency + explicit acks | B11/B12/B23 | ack is the broadcast echo; duplicate submit double-applies or spuriously rejects |
| Actor model + audit fields | B26/B28 (refined) | `by` only; no actorType/initiatedBy/approvedBy/operationId/requestId |
| Reconnect resilience + snapshot-anchored rooms | B22 | no pending-op queue, no reseed below the log floor, snapshots implemented but never wired, `GET /:id` missing `latestSeq` |
| Asset metadata store | — | `assets` table exists, `pg-assets.ts` does not; metadata evaporates on restart (production-safety class) |

**Decisions applied:** roles stay `owner/editor/viewer` (no commenter/admin/guest/`can()`); hierarchy stays org→board (no workspace tier — `workspace` already means the canvas document); AI is **not** a room participant — it is an actor type on the log, with the refined accountability model.

## Batches (ordered by the dependency chain: protocol → actor → proposals → resilience → proof)

### Batch 1 — Operation protocol: requestId, ack, idempotency, operationId

**Schema** (`packages/server/migrations/0017_*` via `npm run db:generate -w @lucent/server`): `op_log` gains `operation_id text not null` (`op_…`, server-generated per committed entry), `request_id text` (client-generated `req_…`, nullable for legacy/MCP), and a partial unique index `UNIQUE (board_id, request_id) WHERE request_id IS NOT NULL`.

**Server**:
- `pg-boards.ts` `appendOp` CTE: on request_id conflict, return the existing seq as `{ok: true, seq, duplicate: true}` — a replayed request is a no-op with the original ack, never a second effect.
- `room.ts` `Room.commit(userId, ops, label, meta?)`: accept `{requestId}`; thread through the allocator; return it in the result.
- `realtime.ts`: `op` messages gain optional `requestId`; new ack message `{type: "op-ack", requestId, seq, operationId, duplicate}` on acceptance; `op-rejected` gains `requestId`, `seq`(head), `operationId: null`. The broadcast echo stays (peers still learn from it).
- REST `POST /api/boards/:id/ops` (`routes/boardOps.ts`): accept + echo `requestId`, same idempotency.
- In-memory `BoardStore` (`boards.ts`): mirror with a per-board `Map<requestId, seq>`.

**Web** (`boardSync.ts`): generate `req_…` per commit; keep a pending map requestId→batch; surface ack/rejection with correlation. Rejected batches currently leave local state silently ahead — on a rejected ack, trigger a targeted resync (fetch board) when the socket is online and no other local edits are unacked; otherwise toast as today.

**Tests**: unit (allocator duplicate → same seq, no double apply — including duplicate MOVE_NODE which today double-applies), HTTP integration (duplicate REST submit → one row, same ack), WS integration (duplicate `op` frame → one broadcast effect). Postgres-gated suite pins the partial unique index.

### Batch 2 — Actor model: `user | ai | system` + `initiatedBy` + `approvedBy`

**Schema** (`0018_*`): `op_log` gains `actor_type text not null default 'user'`, `actor_id text not null`, `initiated_by text`, `approved_by text`. Backfill: `actor_type='user'`, `actor_id=by`, `initiated_by=by`. `timestamp`/`revision` already exist (`at`/`seq`).

**Model** (`packages/server/src/room.ts` or a small `actor.ts`):
```ts
type OperationActor = { actorType: "user" | "ai" | "system"; actorId: string;
                       initiatedBy?: string; approvedBy?: string }
```
- Human path: `{actorType: "user", actorId: userId}` (initiatedBy defaults to actorId at render time; store only when it differs).
- MCP/`boardOps` path: `{actorType: "user", actorId: caller}` — agents act under the accountable human's token.
- `"system"` reserved for future server-initiated ops (no producer yet).
- `stampAuthorship` semantics unchanged — `by` still feeds workspace authorship; the actor model is log-level accountability, so no workspace data migrates.

**Surface**: the log/history listing and `BoardSnapshot` carry the actor; `HistoryView` renders `✦ Lucent created 4 nodes · requested by Alex · approved by Sarah` for `actorType: "ai"`. `assistant` stays the workspace-level author id.

**Tests**: log rows carry the full actor shape on each path; backfill migration test in the pg-gated suite.

### Batch 3 — Server-side proposals (the P2 boundary, the headline)

**Schema** (`0019_proposals`): `proposals` table — `id prp_…` PK, `org_id` FK (tenant boundary), `board_id` FK cascade, `meeting_id` nullable, `status` (`pending|approved|rejected|superseded`), `operations jsonb`, `request text`, `explanation text`, `provenance jsonb` (quote/turnRange/turnKinds), `created_by`, `created_at`, `decided_by`, `decided_at`, `applied_seq bigint` (links the decision to the exact log entry). Plus `UNIQUE (board_id) WHERE status='pending'` — the one-pending-per-board invariant becomes race-safe in the database.

**Store**: `ProposalStore` interface (create-with-supersede, listForBoard, get, decide) + `pg-proposals.ts` + in-memory twin, wired through `makeStores`. `create` atomically supersedes any pending predecessor (replacing the client's `openProposalIn`). `decide` is transition-guarded server-side — deciding an already-decided proposal returns its current state without re-applying (the server-side `decidedRef`). History is retained in full server-side; list returns latest first.

**Routes** (`packages/server/src/routes/proposals.ts`):
- `POST /api/boards/:id/proposals` (editor floor) — body `{operations, request, explanation?, meetingId?, provenance?}`.
- `GET /api/boards/:id/proposals` (viewer floor — everyone in the room can see what Lucent proposes).
- `POST /api/boards/:id/proposals/:pid/approve` and `/reject` (editor floor, CSRF). Approval: re-validate ops against the **current** workspace, commit through `Room.commit` (so it broadcasts through the existing pipeline) stamped `{actorType: "ai", actorId: "lucent", initiatedBy: createdBy, approvedBy: decidedBy}`, then record `{status, decidedBy, decidedAt, appliedSeq}`.

**Realtime**: two new broadcast messages — `proposal-created {id, summary, operations}` and `proposal-decided {id, status, appliedSeq}` — so every connected client's review panel opens/updates live (B27).

**Core move**: `applyValidOperations` (partial re-validation) moves from `packages/web/src/workspace.tsx` into `@lucent/core` — the server must not depend on web, and both must re-validate identically.

**Web** (`workspace.tsx`, `MeetingView.tsx`, `persistence.ts`):
- Server-adopted boards (syncRef active): proposal create/decide go through the REST API; rehydrate on board load from `GET /proposals`; listen for the two new WS messages so peers see the panel. The client `claimDecision` guard stays as belt (the server is the strap).
- Provenance stamping moves to **creation**: the meeting loop stamps `metadata.meeting` onto new nodes' `CREATE_NODE` ops before POSTing, so when the server applies the proposal, every approver's board reproduces the stamp (skipped/stale ops carrying harmless metadata is fine).
- Local (offline) projects keep the localStorage path unchanged.

**Acceptance tests** (the advisory's named case, as automated HTTP+WS integration): Alice creates proposal → hard refresh → proposal remains (server round-trip) → Bob (second session) sees it via broadcast → Bob approves → **exactly one board commit** (one log entry, `applied_seq` set, actor `ai/lucent/initiatedBy Alice/approvedBy Bob`) → both sockets at the same seq.

### Batch 4 — Reconnect/resync + snapshot-anchored rooms

**Server**:
- Wire the implemented-but-never-called snapshot path: `realtime.ts` room rebuild uses `latestSnapshot(boardId)` + log tail via `Room.fromSnapshot` instead of replaying the full log; on room eviction (last participant leaves), `putSnapshot(boardId, room.version(), workspace)` so the next join is cheap (ADR 0010's intent).
- Reseed: if a client's `fromSeq` is below `baseSeq` (log pruned past their cursor), answer a new `{type: "resync", workspace, version}` message instead of a silently partial catchup. `BoardSync` handles it by replacing state wholesale.
- `GET /api/boards/:id` includes `latestSeq` (the store comment already promises it) so a first join knows its revision before the socket opens.
- Surface the existing `error` message client-side (e.g. board deleted by evict) instead of dropping it.

**Web** (`boardSync.ts`): formal state machine `connecting → online ⇄ offline → syncing`; **pending-op queue** — `send()` queues while the socket is closed (today it silently drops), and on reconnect, after catchup, replays the queue **with the original requestIds** so Batch 1's idempotency makes replay exactly-once (if an op actually landed before the drop, the replay returns the original seq as a duplicate no-op).

**Tests**: disconnect mid-queue → reconnect → replay → no duplicate effect (one log row per requestId); `fromSeq` below the snapshot floor → resync replaces state; eviction → snapshot written → next join rebuilds from it (pg-gated).

### Batch 5 — Definition-of-done: the Stage B end-state, proven

The advisory's scenario as an automated cross-stack test (Playwright two-browser spec + HTTP/WS integration under it):
two users, one org, one board → both see the same board and each other's cursors → meeting runs → AI extraction → proposal POSTs → **both browsers show "Lucent proposes N changes"** → the second user approves → both boards converge to the same revision → approving browser refreshes, everything persists → the other disconnects 30s (ops queue) → reconnects → replay+catchup → nobody loses anything, no duplicate commits.

Plus the docs: ADR for the actor model and one for server-side proposals; `docs/17` amendment recording that Stage B was opened by owner decision on the audit (the platform-core gaps were engineering-verified, not user-demanded — say so honestly) and that it closes the P2 boundary; `docs/checklist.md` entries per batch; changesets (`@lucent/server`, `@lucent/core`, `@lucent/web` minor).

### Batch 6 (separable) — Asset metadata store (production-safety completion)

`store/pg-assets.ts` implementing the existing `AssetStore` interface against the existing `assets` table; wire in `makeStores` when Postgres is on; keep in-memory otherwise. Content-addressed `storageKey` (checksum) means rows are stable across restarts; the documented backend-swap caveat (bytes must migrate with a backend change, or re-upload dedupes) goes into the restore runbook. Tests in the pg-gated suite. Ships independently of Batches 1–5 — drop it from the milestone if it slips without blocking anything.

## Explicitly deferred (recorded in docs/17 with reasons)

- **commenter/admin/guest roles + `can()` matrix** — open when a real team says "discuss without edit".
- **Workspace tier (org→workspace→board)** — open on a real folder-limitation complaint; `workspace` name collision with the canvas document stands.
- **Magic-link login** — password+TOTP+OAuth+SAML already exceeds the login matrix.
- **AI presence / room participation** — actor typing delivers the auditability; presence is a UX call for later.
- **Server-derived undo inverses (B21)** — per-client undo already scopes to own ops; the re-attribution cost is documented in `authorship.ts`.
- Sticky sessions (LISTEN/NOTIFY fanout + presence mirror cover multi-instance today), SCIM groups, seats/storage/history-depth enforcement, MCP-over-HTTP.
