## Postgres persistence for the Lucent server

**Goal:** accounts, boards, and the realtime op log survive a server restart. Authenticated collaboration already works end-to-end (verified earlier in this session); what's missing is that the entire server state lives in per-process `Map`s. This PR swaps the in-memory store for Postgres behind the existing `UserStore` / `BoardStore` interfaces. The web app is unaffected — the REST + WebSocket contract is preserved.

**Out of scope (deferred to a follow-up PR):** S3 / image-asset storage. Nothing in the MVP actually persists user uploads yet, so the cost of including S3 now exceeds the benefit.

---

### Stack

- **`drizzle-orm`** for type-safe queries and a real migration story (drizzle-kit).
- **`pg`** (node-postgres) as the driver underneath.
- **CI Postgres:** a `postgres:16` service in the test workflow; `LUCENT_TEST_DATABASE_URL` is set for the server test step.

### Files added

- `packages/server/src/db/schema.ts` — Drizzle schema: `users`, `organizations`, `memberships`, `boards` (with `workspace jsonb`), `op_log` (with `ops jsonb`, `seq integer`, `by`, `label`, `at`, primary key `(board_id, seq)`).
- `packages/server/src/db/client.ts` — `createDb(url)` returning the Drizzle client + a `Pool` for cleanup; reads `LUCENT_DATABASE_URL`.
- `packages/server/src/db/migrate.ts` — `migrate(db)` runs the generated migrations idempotently on boot. Fail-loud if the DB is unreachable.
- `packages/server/src/store/pg-users.ts` — `PostgresUserStore` implements the existing `UserStore` interface. The `lower(email)` unique index replaces the in-memory `byEmail` map.
- `packages/server/src/store/pg-boards.ts` — `PostgresBoardStore` implements `BoardStore` plus the new op-log methods (`appendOp`, `loadLog`).
- `packages/server/drizzle.config.ts` — drizzle-kit config.
- `packages/server/migrations/0000_init.sql` (and follow-ups) — generated by `drizzle-kit generate`, **committed to the repo** so the boot path is `git clone && run` and CI doesn't need a codegen step.
- `packages/server/test/pg-store.test.ts` — Postgres-impl integration tests, gated on `LUCENT_TEST_DATABASE_URL`. Each test runs inside a transaction that's rolled back at the end (via a per-test connection) so tests don't depend on each other.
- `packages/server/test/pg-bootstrap.test.ts` — boots the real `main.ts` against a Postgres, signs up a user, opens a board, sends a WS op, kills the process, restarts, re-joins, and asserts the op is replayed from the log.

The room keeps its existing in-memory log; persistence is the store's job.

### Schema details

```sql
users (id text PK, email text NOT NULL, name text NOT NULL,
       password_hash text NOT NULL, created_at bigint NOT NULL);
-- unique index on (lower(email))

organizations (id text PK, name text NOT NULL, created_at bigint NOT NULL);

memberships (user_id text FK→users, org_id text FK→organizations,
             role text CHECK in ('owner','editor','viewer'),
             PRIMARY KEY (user_id, org_id));

boards (id text PK, owner_id text FK→users ON DELETE CASCADE,
        name text NOT NULL, workspace jsonb NOT NULL,
        created_at bigint NOT NULL, updated_at bigint NOT NULL);
-- index on (owner_id, updated_at desc)

op_log (board_id text FK→boards ON DELETE CASCADE,
        seq integer NOT NULL,
        ops jsonb NOT NULL, by text NOT NULL,
        label text NOT NULL, at bigint NOT NULL,
        PRIMARY KEY (board_id, seq));
```

`boards.workspace` stays a single JSONB blob (matches the in-memory shape, no schema changes to `@lucent/core`). The op_log is what makes collaboration restart-safe: a reconnecting client gets `catchup = room.since(fromSeq)`, and the room's internal `log` array is rebuilt from the DB rather than starting empty.

### Behavioural contract preserved

- **Web app:** zero changes. `boards.ts` and `boardSync.ts` use the same REST/WS shapes; the server swap is transparent. I'll re-run the two-client collaboration script (`scripts/e2e.ts` from the earlier session) to confirm.
- **MCP server (`@lucent/mcp`):** untouched. It holds its own in-memory board, drives the validator/reducer directly, and never talks to the main server's storage. No change needed.
- **Auth:** the existing scrypt hashing and HMAC tokens are unchanged. Tokens are stateless, so they survive a restart as long as `LUCENT_SESSION_SECRET` is stable.
- **Multi-process:** the WebSocket room is per-process (it has to be — presence is live). With persisted state, two server processes can each serve their own WS clients and both see the same boards, because every accepted op is `appendOp`-ed before the broadcast. The remaining gotcha is "two processes that both have the same board's room hot" — they would split live state. The answer is sticky sessions at the LB; this is documented in `docs/06` as a future concern, not solved in this PR.

### Risks + mitigations

- **Per-op workspace write is expensive on large boards.** Every accepted op currently does `boardStore.put({...board, workspace: room.current()})` (see `realtime.ts:160`). On a 1000-node board that's a full JSONB write. Documented as a deferred item ("debounced snapshot flush"); not solved in this PR. The op_log makes correctness independent of this — even if the snapshot write lags a beat, the log is authoritative for replay.
- **Drizzle-kit and migrations in CI.** Drizzle's generated SQL is committed, so CI never runs the codegen step. The `db:migrate` script is the only thing CI invokes.
- **Cold-start race.** Two clients that join at the same instant could both rebuild the room from the same `version` and double-broadcast catchup. The existing `RealtimeServer.rooms` cache is per-process; the doc says "sticky sessions" and the code does `boardStore.get` on every `join`, so the race is bounded. The plan doesn't change this — it's the right answer for now.
